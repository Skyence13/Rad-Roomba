# Planning registers, design 0.4 (README)

Design 0.4 is the system design after the 0.3 baseline (commit `38d1010`), built on the architecture in `docs/architecture/SYSTEM_ARCHITECTURE.md` and the contract `interface/system/contract.yaml` (0.4.0-draft9). Every file here is **new**; none of the 0.3 baseline files was changed. Nothing in 0.4 is physically measured: evidence classes are the contract's `calculated`, `simulated`, `tool-checked`, `physically-measured`, `pending`. **Every verification test is `Planned` with evidence class `pending`**; `check_registers_0.4.py` fails if any test is anything else. Where a row gives a number it says whether it is calculated, simulated, tool-checked, a datasheet value, assumed or UNVERIFIED.

Last revised 2026-11-27 (second pass, after the two independent reviews, board stage 3, firmware, the production body backlog items IB-55 to IB-70 and the follow-up traction-inhibit review `docs/reviews/REVIEW_traction_inhibit_followup.md`). Sources are named in each row (`design_response_0_4`, `evidence_reference`, `source_file_0_4`, `resolution_and_reference`).

## Known limits of this register

* The firmware, ROS 2 workspace and mechanical work packages are cited as the sources state them (lead-verified builds are called "lead-verified" there); the native-emulator scenarios currently fail in bring-up against the stage-3 chassis firmware (IB-46) and the unexplained localisation transient (IB-47) is open: both appear as risks (RSK-053, RSK-056) and tests (VT-066, VT-067, VT-068).
* No test has been run. The words "simulated" and "calculated" in a row describe a model or an emulator, never a measurement.

## Reproduce the consistency checks

```bash
python3 planning/bom_0.4/extract_board_boms.py
python3 planning/bom_0.4/extract_mech_boms.py
python3 planning/check_registers_0.4.py
```

`check_registers_0.4.py` (read-only) checks that every ID is unique, that baseline rows and columns are preserved (only the documented fields differ), that every requirement, test, decision and risk reference resolves and that links are two-way (requirement and test, decision and requirement), that every test is `Planned` with evidence class `pending`, that every cited IB, VT, RQ, DEC and RSK number exists (the backlog is read), that every new or revised row cites a source file that exists and says what changed, that every new test has a method and a criterion or an explicit "criterion not yet defined", that every new risk has cause, consequence, control, residual rating and test, that BOM status classes are from the fixed vocabulary and every generated board BOM reference is present, and that the RFQ carries the new figures.
